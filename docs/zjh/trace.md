# 炸金花决策留痕

对应 `BOT-BRAIN-DESIGN-2026-09-03.md` §4.11。一句话：**牌桌上发生的每一次决定，都要能事后调出来看**——机器人当时的情绪、冲动、有没有动脑子、为什么改主意；真人当时面对的局面和他花了多久。调优靠这些数据，不靠回忆。

三条不可逾越的线，看代码之前先记住：

1. **留痕绝不能影响牌局。** 取样、入队、写库全程 try/catch，失败只 `console.error`。写库炸了牌局照常打完，这一条有测试（`tests/zjh-trace.test.ts` 的「写库炸了，牌局照样打完」）。
2. **留痕不能变成偷看通道。** 真人的牌面在亮牌前一个字都不进库——不是「记了但不给看」，是表里压根没有那几列。连客观牌力都要等亮牌之后才回填。
3. **只读复盘。** `scripts/zjh-review.ts` 不写任何一行。

---

## 1. 数据长什么样

三张表，和 `zjh_memory` 同一个库（默认 `zjh.db`，可用 `ZJH_DB` 指定），建表在 `server/store.ts` 的 `createTraceTables()`。

粗特征**摊平成列**而不是塞进一个 JSON blob：复盘要按「同一个粗特征下机器人和真人分别怎么打」分桶排名，那是一句 `GROUP BY` 的事；存成 JSON 就得把整张表读进内存自己分组。只有真正的可变长结构（情绪向量、规律列表、对手快照）才用 JSON 列。

### 1.1 `zjh_decisions`——机器人的每一次决策

一行 = 一次决策，**含非回合动作**（§4.6 的抢跑 `look`/`fold`，用 `off_turn` 区分）。

| 列 | 含义 |
|---|---|
| `at` / `room` / `hand_no` / `round_no` | 什么时候、哪一桌、第几局、第几轮 |
| `memory_key` / `persona` | 谁（长期记忆键，形如 `bot:老王`）、他用的哪张人物卡 |
| `off_turn` | 1 = 还没轮到他，是他自己在旁边顺手做的 |
| `self_tier` | **主观**牌力：他*觉得*自己的牌有多好（过了人物卡原型表和情绪） |
| `strength` | **客观**牌力分位。闷着没看牌的时候是空的——他自己都不知道 |
| `threat_tier` / `story` | 他觉得对面有多凶 / 桌上这一局最凶的那条动作串讲到哪 |
| `stake_tier` / `cost_fraction` / `pot` / `unit_tier` / `pot_maturity` | 这一步要掏多少、占身家多少、池子多大多熟、当前单价档 |

> `cost_fraction` 是**比例，永远落在 0..1**（2026-09-04 P2.1 收口）。
> 它算的是「这一口的名义价钱 ÷ 手上还剩多少」，而名义价钱不管你兜里够不够：
> 筹码被打短的时候引擎会把这一口自动缩成 allIn，但名义价钱照样可以是身家的几倍——
> 早期留痕里量到过 47 行 > 1、最大 400000。这个数会原样流进「看牌」的成本项和 `atRisk`，
> 把「贵不贵」顶到饱和之外。语义上「把整副身家推进去」已经是最贵、再贵没有意义，
> 所以在 `situation.ts` 的源头 `clamp01`。`tests/zjh-trace.test.ts` 逐行断言这个区间。
| `familiarity` / `standing` | 这个局面对他多熟（R29 认知流畅）／他现在是赢着还是输着（参照点，R1/R27） |
| `active_count` / `position` / `blind` | 还剩几个人、位置、闷着还是看过 |
| `counterpart_key` | 现在压着他的那个人 |
| `opponents` | JSON：每个对手的原型名、slope、可信度、这一局讲的故事、范围模型算出的威胁、记的仇 |
| `emotions` / `drives` | JSON：七情 E_t 与驱力 D_t |
| `tilt` / `ease` / `arousal` / `fatigue` / `willpower` | 情绪的五个标量投影 |
| `impulse_key` / `confidence` / `felt_strength` / `felt_threat` | **系统 1**：脱口而出的那个动作、他有多确信、感到的牌力与威胁 |
| `p2` / `engaged` | **系统 2** 的介入概率与是否真的介入了 |
| `deliberate_key` / `deliberate_score` / `difficulty` | 系统 2 的结论、打分、这一步有多难算 |
| `overridden` / `gap` / `need` | 是否推翻了直觉；推翻的门槛：只有 `gap > need` 才推翻，`need` 来自自控力 |
| `deviated` | 是否偏离了本局的线路。**三态**：没开系统 2 又没有对照时写 NULL —— 不知道就是不知道，不许默认算成「没偏离」 |
| `fired` | JSON 数组：这一步触发的规律编号（R1–R33） |
| `plan` / `plan_commit` | 本局的线路名与承诺强度 |
| `action` / `action_unit` / `target_id` | 最终动作（`raise` 带单价，`compare` 带目标） |
| `think_ms` | 表现出来的思考时间（已经过人味塑形，不是纯计算耗时） |

### 1.2 `zjh_human_actions`——真人的每一次动作

只记 `look` / `call` / `raise` / `fold` / `compare` / `all_in`，也就是牌桌上真的做了一件事的那几个。

字段是 `zjh_decisions` 的**特征子集**，加上两个真人专属的：

| 列 | 含义 |
|---|---|
| `account_id` / `memory_key` | 账号（可能为空）与长期记忆键（`acc:<账号>` 或 `local:<座位 id>`） |
| `elapsed_ms` | **真实反应时间**：从上一次**牌局状态变化**到他按下去（见 2 里的 `markChange`；presence 之类的空广播不重置） |
| `looked` | 这一刻他看过牌没有 |
| `strength` | **亮牌前恒为空**，结算时只给亮过牌的人回填 |

**没有** `self_tier`：那是「他觉得自己牌多好」，要算它就得读他的牌。这里刻意不算。

特征是怎么打出来的：真人套一张固定的「常人」卡（`COMMON_PERSONA`）和一份全新的中性心理状态，走**和机器人同一个** `coarse()`（`shared/zjh/bot/trace.ts` 的 `traceHuman`）。这是一把固定的尺子——「一个普通人坐在这个位置上会感到什么」——所以两边的格子可比。它**不是**在猜这个真人的内心；机器人那一侧是被自己人物卡和情绪扭曲过的主观视角，两边在这一点上天然不对称，读 (b) 那一段时要记着。

### 1.3 `zjh_hand_outcomes`——每局结算

`UNIQUE(room, hand_no)`，一局只有一行。

| 列 | 含义 |
|---|---|
| `winner_key` / `winner_name` / `pot` / `reason` | 谁赢、赢多少、怎么赢的 |
| `players` | JSON 数组：每个人的 `bet`（投入）/`net`（收益）/`delta`（净变化）/`revealed`（亮没亮牌）/`strength`（亮了才有） |
| `emotion_delta` | JSON，按 `memory_key`：结算这一下把每个人的 E_t / D_t 推动了多少 |

`emotion_delta` 是结算后的心理状态与本局最后一次决策时状态的差值。局中事件已经走 `feelHand → appraise → nudge`，结算走 `settle`；两条路径共用通用评价映射。它只表示结算这一刻的增量，不能拿它代替整局情绪轨迹。P3 的 `opponents.archetype` 可能记录公开归类得到的人物名；身份键按账户或机器人名字稳定保存，原始真人行仍不含未公开牌面。

## 2. 数据是怎么进去的

写入层是 `server/trace.ts` 的 `TraceRecorder`，三个入口，全部挂在 `server/rooms.ts` 上：

| 入口 | 挂在哪 | 时机 |
|---|---|---|
| `bot(state, record, cmd)` | `runZjhBot` / `runOffTurn` | 动作**落地之后** |
| `human(state, player, cmd, elapsedMs)` | `command()` | 动作**生效之前**取样，返回一个提交函数，生效之后才调 |
| `hand(state)` | `traceZjhHand`（`broadcast` 里，round_end） | 每局一次，`Room.traceHand` 挡重复 |

几个刻意的选择：

- **机器人那份 `record` 是从 `decide()` 一路透出来的**（`decide.ts` → `BotAction.record` → `BotMove.record` → `rooms.ts`），不是事后拿状态重算的。重算出来的不是他刚才面对的那个局面，而且会多抽随机数、把 `actionSeq` 搅乱。
- **真人必须在 `applyCommand` 之前取样**：状态一改，「他是顶着一次加注按的弃牌」就找不回来了。但落库要等动作真的做成——指令被引擎拒掉（不该他动、跟不起、比牌没解锁）时一行都不写。这就是「返回提交函数」这个别扭形状的原因。
- **入队是纯内存操作，SQL 攒到下一个 tick 成批跑**（200ms 一批，一批一个事务）。牌桌那一步早就返回了。
- **`Room.changedAt`** 只在牌局状态**真的变了**的时候刷新（`Hub.markChange`，挂在机器人落子、非回合动作、超时弃牌、开局/新一局这几条走过 `eng.apply` 的路上），`elapsed_ms` 就是 `Date.now() - room.changedAt`——从他看到新局面到他按下去。上下线、进房、房主移交同样会广播，但牌桌一张牌都没动，**不碰这个时钟**：一个正在想牌的人不该因为别人掉了个线就被记成「刚看到局面」。
- **走 `command()` 的指令还要再过一道**：`markIfTableChanged` 拿 `eng.apply` 前后的**牌桌指纹**（`tableFingerprint`）比一比，真变了才刷。表情就是典型——它是一条正经指令、会广播、也进快照，可牌桌一张牌都没动，而真人边想边发表情是牌桌上最常见的事，让它冲时钟会系统性地把反应时间压短。`rename` 同理。指纹里刻意不收昵称、头像、在线状态、表情、`log` / `actionSeq`。用指纹而不是「哪些指令不算数」的名单，是为了以后加新指令时不需要有人记得回来改名单。
- **结算写库也是异步的**：`hand()` 里行和回填值的**计算**是同步的（`state` 下一拍就变了，晚一步取不到），但写库跟决策/动作走同一条队列。一批里的顺序是定死的——先决策/动作，再结算行，最后回填，因为回填要改的正是同一批刚写进去的真人动作行。

失败处理只有一种：`console.error`，然后丢掉这一批。不重试（重试只会在下一次再挂一遍）、不抛出去、不影响任何人。

## 3. 保留与归档

- 保留 **30 天**。
- 超期的行按 `hand_no` 排序归档成 **JSONL**，每行 `{"t":"decision"|"human"|"outcome", ...}`，文件名带时间戳。
- **先写文件，写成功了才删行**——宁可留着占地方，也不能把唯一一份数据删掉。
- 启动时跑一次，之后每 24 小时一次。失败只打日志。
- 归档目录：`ZJH_TRACE_ARCHIVE`，默认是数据库同级的 `trace-archive/`。**没配到目录就什么都不做**（没地方放的时候不删）。

代码在 `Store.archiveTrace()` 与 `TraceRecorder.startRetention()`；`server/main.ts` 启动时接上，`shutdown()` 里 `hub.trace.stop()` + `flush()` 把队列里剩的写完再走。

## 4. 怎么复盘

```
node scripts/zjh-review.ts [--db <路径>] [--since <天数|日期>] [--room <房号>] [--hand <局号>]
```

- `--db`：默认 `$ZJH_DB`，再默认仓库根的 `zjh.db`
- `--since 7` 或 `--since 2026-09-01`
- `--room TRACE1`
- `--hand 12`：在五块之后**额外**打这一局的逐步全轨迹

输出是 Markdown，直接重定向成文件就能看：

```
node scripts/zjh-review.ts --since 7 > /tmp/review.md
```

五块内容（§4.11.2）：

**(a) 人味统计**——§6.4 各项，机器人和真人分开算、走同一段代码。入池率、加注率、遇压弃牌率、闷牌率、闷到第 3 轮占比、闷比/闷弃占比、大牌早比、梭哈率、平均用时、收官人数。表里带着 §6.4 的目标区间，一眼能看出哪一项跑偏了。

留痕表看不到的两项在报告末尾明说了：每局表情次数与连续同表情率（表情不走决策留痕），六台机器人的四维两两距离（要多局自对弈的独立跑批）。这两项仍由 `tests/` 里的形状测试把关。

**(b) 分布差异排行**——把每一步归到一个粗特征格子（轮次 / 闷看 / 威胁档 / 下注压力档 / 人数），比较机器人和真人在同一个格子里的动作分布，按**总变差距离**排序。差异最大的格子就是「不像人」的候选。格子只用两边都有的维度（不含 `self_tier`）。任一侧样本 < 10 的格子会标 ⚠——那种差异多半是噪声。

**(c) 情绪轨迹与规律频次**——按机器人分节：五个标量的均值、系统 2 介入率与推翻率、偏离线路率、非回合动作占比、最近 12 局的 tilt/ease/意志力轨迹、每条规律触发了多少次、结算触发的情绪增量均值。

**(d) 真人原型归类**——用 `shared/zjh/bot/profile.ts` 的 `archetypeOf` / `credibility`，也就是**机器人读人用的同一把尺子**，把结论打出来。置信度按长期档案的局数分三档：< 3 局是「样本不足，按常人处理」（`archetypeOf` 自己就退回常人了，这里把「为什么是常人」摊开说，免得把「不知道」读成「他就是个普通人」），< 20 局是「档案还浅」。

**(e) 可疑瞬间**——四条规则：系统 2 没介入却做了大动作（梭哈/比牌/掏 12% 身家以上的加注）、tilt ≥ 0.7 时的动作、fear ≥ 0.75 时的动作、同一个人在同一个粗特征格子下连续 ≥ 3 次同一动作。

**`--hand N` 的全轨迹**——机器人和真人的步骤按时间交错排。每一步展开：局面（主客观牌力、威胁、压力、熟悉度、站位、池子、人数）、情绪五标量与 E_t/D_t、系统 1 的冲动与三个感受值、系统 2 是否介入及其结论与 gap/need、线路与偏离、触发的规律。末尾附结算表。

这就是「用户口头反馈 → 数据回答」的路径：他说「第 12 局那个机器人不像人」，就 `--hand 12`，把那一步的完整 trace 摆出来。

## 5. 测试

`tests/zjh-trace.test.ts`，跑「五个机器人 + 一个真人」的真牌局：

- 三张表都落到位，每一行的关键字段都不为空；
- 真人亮牌前 `strength` 是空的，表里**没有**牌面类的列，牌面也没藏在 `opponents` 里；亮牌后才回填；
- 信息边界：把所有没亮给他看过的对手的牌换掉（连亮给他看过的也换掉），`traceHuman` 产出的 `features` / `opponents` 必须逐字段相等；他闷着的时候连他自己的牌换掉也得相等。反过来，池子和注档一动特征必须跟着动——证明这不是一句恒等式；
- 写库炸了（`sync: true` 把 SQL 放回牌桌的调用栈上，最危险的形态）牌局照样打完、结算照出；
- 取样炸了同理；
- 非 sync（生产形态）下 `hand()` 返回时库里还没有这局的结算行，`flush()` 之后才有——证明结算没在 `broadcast` 的调用栈上写 SQL；
- 真人用时的起点：想牌期间别人发一个表情、再掉一次线，记到的 `elapsed_ms` 三段等待都算进去，不被这两下重置；
- 五块复盘都出得来，`--hand` 打得出全轨迹，`--room` / `--since` 过滤正确；
- 结算防重：同一局写两次只留一行；
- 归档：没超期一行不动，超期的先写 JSONL 再删，行数对得上。

发牌是随机的，真人完全可能在轮到自己之前就被比掉。所以测试里的 `playUntilHumanActs`
是**一局一局往下开、直到他真的动过一次**才断言，而不是赌第一局就轮得到他——
不这么写的话，同一个断言单跑能过、全量跑会红。
